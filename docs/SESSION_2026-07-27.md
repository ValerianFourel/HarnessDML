# Session log — 2026-07-27

A monitoring session that turned into a rescue. It started as "give me the
commands to check the state of the experiment on JUPITER" and found that the
dashboard was green while a third of the planned work had never been
submitted, four finished arms were unharvested, and the two headline
percentages were both wrong — one by 43 points. It ended with an unplanned
venv incident (ADR 24) and the whole roster launched.

TL;DR: progress reporting was rebuilt so it can be trusted (per-spec targets,
in-scope de-duplicated counts, a per-model roster, stall detection); the gate
matrix became machine-readable and the three giants were gated IN on all
twelve bands; wave-2 (never launched) and wave-3 (never written) went out
along with the two arms the spec required and nobody could run; 43 finished
slices were harvested into git; and a mid-flight `huggingface_hub` change
killed new servers until the preflight was taught to walk the real import
chain.

---

## 1. WHAT THE OLD VIEW COULD NOT SEE

`status.sh` (previous session) answered "is anything running". The first
version of `overview.sh` added quotas, outcomes, server health and results.
Both counted rollouts with `wc -l`, and that number cannot express progress:

* **Each experiment has its own denominator.** The 4-config thin arm was
  scored against the 32-config grid target and read **13%** while being
  complete. Every arm (padding 6 configs, template 6 configs x 50 tasks,
  temp0 4 configs x 3 seeds) read `-` or nonsense.
* **A capped slice runs past 100%.** HotpotQA is the only band whose pool
  (7405) exceeds the `n_tasks: 3000` cap, so only it can hold orphans —
  rollouts on tasks that left scope when the cap landed (ADR 20). qwen x
  hotpotqa read **150.3%** with 68,000 rollouts still to run.
* **Duplicates are invisible to `verify`.** Adding `padded_components` to the
  cell identity re-keyed every rollout, so each pre-padding slice re-ran its
  wave-1 tasks once — exactly 16,000 rows for a 32x100x5 slice. `rollout_key`
  stays unique (which is all `verify` checks); only `(cell, task, seed)`
  repeats, giving 100 tasks k=10 against everyone else's k=5. → **ADR 22**.

Consequence in the field: **mistral x hotpotqa read 97.5%, then 100%. Deep
says 57.1%** — ~206,000 rollouts, not ~12,000. The gaps list had been
reporting "11,846 rollouts left" for a slice missing twenty times that.

## 2. WHAT REPLACED IT — `harnesslab/progress.py`

* `slice_target(spec, bench)` = configs x in-scope tasks x seeds, read from
  the slice's OWN spec (resolved from the store path: stores live at
  `$SCRATCH/harnesslab/<spec-basename>/rollouts_<model>_<bench>`).
* `--deep` scans the store: in-scope, unique `(cell, task, seed)`, orphans,
  duplicates, corrupt lines. Uniqueness is a set of `hash(tuple)` — 60 MB
  instead of ~1 GB on a census store.
* `unit_key()` normalizes a **missing** `padded_components` to `''` exactly as
  `aggregate` does. Without it a row and its re-keyed twin were two different
  units: qwen/musique reported 394,460 unique against a 386,720 target with
  zero duplicates — impossible, and the tell that found the bug.
* `summarize()` — done/target/% per model and a TOTAL, each slice capped at
  its own target so an orphan-inflated store cannot push the census past 100%.
* `roster()` — one line per **registry** model (all 20), so models with no
  store still appear. Tier, pilot y/n, gate ruling and progress per band,
  done/target. Storeless gated models get their target from the ruling, which
  is where the 9,370,540-rollout programme total comes from.
* `STALL?` — an unfinished slice nothing has written for >4 h, sorted first in
  the gaps table. ministral/gsm8k had sat at 62.7% with an exhausted chain for
  7 h looking exactly like healthy progress; it also caught mistral/math one
  rollout short after 30 h.
* `gaps()` — gated slices with no store or an unfinished one, each with the
  exact submit command.

CLI: `progress [--deep] [--only] [--roster]`, `roster [--deep]`, and
`status --tasks/--n-tasks` for a single store. Suppressing gaps under `--only`
was a bug fix: it had called every filtered-out slice "NO STORE".

## 4. THE GIANTS WERE GATED — all twelve bands IN

Their pilots had been complete at 160/160 per band for ~10 h and their retry
probes had passed (1048806/07/25, all emitting textual `Action:`/`Answer:`);
nobody had read the numbers. `scripts/hpc/gate_report.sh <model>` now does it:
aggregates the pilot slices and prints BARE/T per band with the verdict in
ADR 18's order — BARE saturation first (mistral x gsm8k went thin on BARE .875
even though T .60 sat mid-window), then either-arm-in-window, then floor. It
reproduces all five historical rulings.

| model | hotpotqa | musique | gsm8k | math |
|---|---|---|---|---|
| qwen_3_5_122b | .431/.453 | .646/.528 | .750/.875 | .400/.525 |
| llama_4_scout | .314/**.095** | .429/.283 | **.825**/.900 | .575/.600 |
| kimi_linear_48b | .199/.234 | .483/.449 | **.825**/.850 | .400/.350 |

Two flags kept with the data: scout's hotpotqa **T collapse** (.314 -> .095,
the largest negative T effect in the roster — verify it is capability and not
a delivery failure before reading it as a component effect), and .825 BARE on
gsm8k for scout/kimi, inside the window by .025 against mistral's thin-arm
precedent at .875.

(The verdict column printed empty on first run: awk rejects a ternary wrapped
across lines. The numbers were always right.)

## 6. HARVEST — 43 slices into git

`scripts/hpc/harvest_all.sh`: aggregate + verify + commit + push every store,
idempotent, `ONLY=` / `NO_COMMIT=1` / `DEDUPE=1`. It passes
`aggregate --task-scope auto`, which derives the task list and cap from the
store's own spec — harvesting a capped slice by hand without `--tasks` ships
its orphans into the panel.

Harvested: all six control-arm slices (padding x2, ordering, template,
temp0 x2 — every one exactly on target) and all pilot slices, including the
16 that had been sitting on the cluster aggregated but never committed.
`aggregate` also gained duplicate reporting (always) and `--dedupe` (on ask),
since silently changing already-shipped panels is worse than a loud number.

`analysis/model_matrix.sh` prints BARE / T / T+SR+R / All-In for every
(model, band) with a committed panel — the cross-model picture in one screen.
First read: T *helps* qwen-3.6-27b on every band and gsm8k on the giants, and
T *destroys* llama-3.1-8B (.850 -> .175 gsm8k, .187 -> .000 hotpotqa), gpt-oss
(.362 -> .000 musique) and scout on hotpotqa. All-In sits below BARE in most
cells. Sign-flipping across families, visible at pilot size — descriptive
only, no inference.

## 7. INCIDENT — huggingface_hub, mid-census (ADR 24)

New `vllm serve` processes began dying with `ModuleNotFoundError: No module
named 'huggingface_hub.utils._terminal'` while already-running servers kept
answering 200 OK. Five jobs lost at ~2 min (exit 1), six more to the 40-min
ceiling.

**Chain**: `.venv/bin/vllm` -> `vllm.entrypoints.cli.main` -> `vllm.config` ->
`transformers` -> `huggingface_hub.utils.__init__` -> `_cache_manager` ->
`from ._terminal import tabulate`.

**Diagnosis**: the login-node check passed on the same venv and the same
version (1.24.0) that the job had just failed on. That contradiction is the
signature — pip unlinks before it relinks, so a job importing inside the
install window sees `_cache_manager.py` present and `_terminal.py` not yet
written, while the identical import succeeds a second later.

**Two fixes**:
1. `huggingface_hub` is part of the matched instrument set, not a loose
   dependency — `pyproject` bounds it only at `>=0.30`, so any resolve can
   move it under a running fleet. `setup_env.sh` pins it (`HF_HUB_PIN`)
   alongside the torch trio.
2. The ADR 21 preflight imported `vllm` plus a flash-attn extension and never
   touched transformers, so it would have green-lit every failing job. It now
   imports the CLI entry point itself, reports the real exception, and routes
   to the hub fix or the torch fix by matching the message.
   `scripts/hpc/check_env.sh` is the same walk as a standalone command, with a
   per-step trace.

**Operational rule, twice-learned**: never `pip install` while jobs are
starting. Recovery is to fix the venv and let the pending links heal
themselves — every link sources `env.sh` and imports at start, and chains are
resume-safe. Resubmitting instead would put two writers on one store.
